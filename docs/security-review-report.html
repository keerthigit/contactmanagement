Security Review Report: Contact Management System (Spring Boot)

Scope: Provided backend code only
Review focus: OWASP Top 10 aligned issues with real exploitability

Issue 1

1. Issue Title: Unauthenticated access to all contact APIs (missing API authentication and authorization)

2. Severity: Critical

3. CWE: CWE-306 (Missing Authentication for Critical Function), CWE-862 (Missing Authorization)

4. Location: backend/contact-service/src/main/java/com/contactmanagement/contactservice/controller/ContactController.java - Class ContactController - Methods createContact, getAllContacts, getContactById, updateContact, deleteContact, searchContacts; and backend/contact-service/pom.xml (no Spring Security dependency)

5. Problem: Every CRUD/search endpoint is publicly callable with no authentication/authorization checks. There is no security configuration and no method-level access control.

6. Exploit Scenario: An internet user sends direct requests to /api/contacts through gateway or to contact-service and can read, create, modify, and delete all contacts without credentials.

7. Fix: Add Spring Security + resource server JWT validation and enforce role-based rules. Minimal code-level fix:

  • Add dependency spring-boot-starter-security (and JWT resource server dependency) in backend/contact-service/pom.xml.
  • Create a SecurityConfig with a SecurityFilterChain requiring authentication for /contacts/**.
  • Add @EnableMethodSecurity and method guards such as @PreAuthorize("hasAnyRole('ADMIN','USER')") on controller/service methods.

8. Confidence: High

Issue 2

1. Issue Title: Broken object-level authorization (IDOR) across read/update/delete/search operations

2. Severity: High

3. CWE: CWE-639 (Authorization Bypass Through User-Controlled Key)

4. Location: backend/contact-service/src/main/java/com/contactmanagement/contactservice/service/ContactService.java - Methods read, readAll, update, delete, searchContacts; and backend/contact-service/src/main/java/com/contactmanagement/contactservice/model/Contact.java (no owner/user field)

5. Problem: The service fetches and mutates contacts by ID with no owner check, and there is no per-user ownership model in the entity/query layer.

6. Exploit Scenario: A low-privileged USER guesses or obtains another contact UUID and performs GET /contacts/{id}, PUT /contacts/{id}, or DELETE /contacts/{id} to access/alter/delete another user’s data.

7. Fix: Add an owner column and enforce owner-scoped repository queries. Minimal code-level fix:

  • Add ownerUserId (or equivalent) to Contact.
  • Replace findById(id) with findByIdAndOwnerUserId(id, currentUserId) for USER role.
  • In list/search, query only owner’s data (findAllByOwnerUserId(...) / owner predicate in specification).
  • Allow ADMIN bypass explicitly via role check; deny cross-user access otherwise.

8. Confidence: High

Issue 3

1. Issue Title: Mass assignment on create endpoint allows client-controlled primary key and audit fields

2. Severity: High

3. CWE: CWE-915 (Improperly Controlled Modification of Dynamically-Determined Object Attributes)

4. Location: backend/contact-service/src/main/java/com/contactmanagement/contactservice/controller/ContactController.java - Method createContact; backend/contact-service/src/main/java/com/contactmanagement/contactservice/model/Contact.java - Setters setId, setCreatedAt, setUpdatedAt

5. Problem: The API binds request JSON directly to JPA entity and persists it; clients can submit fields that should be server-controlled (id, timestamps).

6. Exploit Scenario: Attacker sends POST /contacts with an existing id to force overwrite/merge behavior or inject misleading audit timestamps, compromising data integrity and audit trust.

7. Fix: Use dedicated request DTOs with allowed fields only; never bind entity directly from request body. Minimal code-level fix:

  • Create CreateContactRequest containing only business fields (firstName, lastName, emails, phones, addresses, tags, status).
  • Map DTO to a new Contact instance in service and do not set id/createdAt/updatedAt from client input.
  • Optionally annotate server-managed fields as read-only for JSON (@JsonProperty(access = JsonProperty.Access.READ_ONLY)).

8. Confidence: High

Issue 4

1. Issue Title: Hardcoded database credentials in source configuration

2. Severity: Medium

3. CWE: CWE-798 (Use of Hard-coded Credentials)

4. Location: backend/contact-service/src/main/resources/application.yml

5. Problem: Database username/password are embedded in committed config, making credential leakage likely via repo access, logs, backups, or artifact distribution.

6. Exploit Scenario: Any actor with code/release access obtains DB credentials and connects directly to PostgreSQL to read/modify contact data outside API controls.

7. Fix: Externalize secrets to environment variables or a secret manager. Minimal code-level fix:

  • Replace plaintext with ${DB_USERNAME} and ${DB_PASSWORD} in application.yml.
  • Inject values at deploy/runtime and rotate current credentials.

8. Confidence: High

Final Summary

Total issues found by severity:

  • Critical: 1
  • High: 2
  • Medium: 1
  • Low: 0

Top 3 risks to fix first:

  1. Missing authentication/authorization on all contact endpoints (public CRUD access).
  2. IDOR due to no owner model and no ownership enforcement in service/repository queries.
  3. Mass assignment via entity binding in create endpoint, allowing client-controlled sensitive fields.
